# 1. Objectif

Ce document définit les spécifications fonctionnelles et techniques du **User** dans MAHLINE.

Le User représente une identité numérique pouvant :

* s'authentifier ;
* accéder à MAHLINE ;
* posséder des rôles et permissions ;
* disposer d'une session authentifiée ;
* utiliser des API Tokens lorsque cela est autorisé ;
* être suivie dans l'historique des connexions ;
* être auditée.

---

# 2. Identité du User

Chaque User possède une identité unique dans MAHLINE.

L'identifiant primaire du User est un **ULID** de 26 caractères.

```text
id
│
└── CHAR(26) PRIMARY KEY
```

L'identifiant ne doit pas être auto-incrémenté.

---

# 3. Données du User

La table `users` contient les données principales suivantes :

| Champ               | Type         | Obligatoire | Description            |
| ------------------- | ------------ | ----------: | ---------------------- |
| `id`                | CHAR(26)     |         Oui | Identifiant ULID       |
| `first_name`        | VARCHAR(255) |         Oui | Prénom                 |
| `last_name`         | VARCHAR(255) |         Oui | Nom                    |
| `display_name`      | VARCHAR(255) |         Oui | Nom affiché            |
| `email`             | VARCHAR(255) |         Oui | Adresse e-mail unique  |
| `telephone`         | VARCHAR(255) |         Oui | Numéro de téléphone    |
| `password`          | VARCHAR(255) |         Oui | Mot de passe haché     |
| `remember_token`    | VARCHAR(100) |         Non | Token Remember Me      |
| `status`            | VARCHAR(255) |         Oui | Statut du User         |
| `locale`            | VARCHAR(255) |         Oui | Locale du User         |
| `timezone`          | VARCHAR(255) |         Oui | Fuseau horaire         |
| `email_verified_at` | TIMESTAMP    |         Non | Date de vérification   |
| `created_at`        | TIMESTAMP    |         Non | Création               |
| `updated_at`        | TIMESTAMP    |         Non | Dernière modification  |
| `deleted_at`        | TIMESTAMP    |         Non | Suppression logique    |
| `created_by`        | CHAR(26)     |         Non | Acteur de création     |
| `updated_by`        | CHAR(26)     |         Non | Acteur de modification |
| `deleted_by`        | CHAR(26)     |         Non | Acteur de suppression  |

---

# 4. ULID

Le User utilise un ULID comme clé primaire.

Contraintes :

* longueur : 26 caractères ;
* type logique : string ;
* unique ;
* non auto-incrémenté.

Le modèle doit utiliser les mécanismes ULID de MAHLINE/Laravel.

---

# 5. Prénom

`first_name` représente le prénom du User.

Contraintes :

* obligatoire ;
* non nullable ;
* longueur maximale : 255 caractères.

---

# 6. Nom

`last_name` représente le nom du User.

Contraintes :

* obligatoire ;
* non nullable ;
* longueur maximale : 255 caractères.

---

# 7. Display Name

`display_name` représente le nom utilisé pour l'affichage du User dans l'application.

Il doit être présent même lorsque le système dispose séparément de `first_name` et `last_name`.

Exemple :

```text
first_name   = Mohamed
last_name    = Alaoui
display_name = Mohamed Alaoui
```

Le `display_name` peut être modifié indépendamment si les règles métier l'autorisent.

---

# 8. Email

L'adresse e-mail constitue l'identifiant d'authentification principal initial.

Contraintes :

* obligatoire ;
* non nullable ;
* unique ;
* format e-mail valide ;
* comparaison et normalisation selon les règles Authentication.

Deux Users ne peuvent pas utiliser la même adresse e-mail.

---

# 9. Téléphone

`telephone` représente le numéro de téléphone associé au User.

Contraintes :

* obligatoire selon le modèle actuel ;
* non nullable ;
* longueur maximale : 255 caractères.

Les règles de validation et de normalisation du numéro sont définies séparément lorsque le module de téléphonie sera spécifié.

---

# 10. Password

Le mot de passe est stocké exclusivement sous forme de hash sécurisé.

Le mot de passe en clair ne doit jamais être :

* enregistré dans la base ;
* écrit dans les logs ;
* enregistré dans Login History ;
* enregistré dans Audit ;
* retourné par une API ;
* exposé dans une réponse HTTP.

Le champ `password` contient uniquement le hash.

---

# 11. Remember Token

`remember_token` est utilisé pour le mécanisme Laravel **Remember Me**.

Il est nullable.

Il ne doit jamais être exposé dans une réponse API ou dans les journaux.

---

# 12. User Status

Le User possède un statut contrôlé par `UserStatus`.

Le statut initial est :

```text
active
```

Le statut détermine si le User peut établir ou maintenir une authentification.

Un User non autorisé ne doit pas pouvoir créer une nouvelle session authentifiée.

---

# 13. Locale

La locale par défaut du User est :

```text
fr
```

Elle détermine notamment la langue préférée pour les fonctionnalités localisées.

Valeur par défaut :

```text
locale = fr
```

---

# 14. Timezone

Le fuseau horaire par défaut du User est :

```text
UTC
```

Valeur par défaut :

```text
timezone = UTC
```

Les dates stockées en base doivent respecter les standards temporels globaux de MAHLINE.

---

# 15. Email Verification

`email_verified_at` indique si l'adresse e-mail du User a été vérifiée.

Valeurs :

```text
NULL
```

ou :

```text
TIMESTAMP
```

Une adresse non vérifiée ne doit pas être considérée comme vérifiée par le système.

Les règles exactes d'accès conditionné par la vérification de l'e-mail appartiennent à Authentication.

---

# 16. Audit

Le User est une entité auditable.

Les opérations importantes doivent pouvoir identifier l'acteur responsable.

Les colonnes d'acteur d'audit sont :

```text
created_by
updated_by
deleted_by
```

Elles sont nullable afin de permettre les opérations :

* système ;
* installation ;
* migration ;
* tâche planifiée ;
* processus automatique ;
* création sans User authentifié.

Les standards d'audit sont définis dans :

```text
AUDIT_STANDARD.md
```

---

# 17. Soft Delete

Le User utilise la suppression logique.

Le champ :

```text
deleted_at
```

permet de conserver l'historique du compte sans supprimer immédiatement l'enregistrement.

Un User supprimé logiquement ne doit plus pouvoir s'authentifier.

La suppression physique doit être exceptionnelle et soumise aux règles d'archivage et de conservation des données.

---

# 18. Authentication

Le User peut être authentifié lorsque toutes les conditions de sécurité sont satisfaites.

Flux général :

```text
User
 │
 ▼
Authentication
 │
 ├── Email
 ├── Password
 └── Status
 │
 ▼
Authenticated
```

L'authentification est définie dans :

```text
AUTHENTICATION_SPECIFICATION.md
```

# 19. Règle de session unique

## ONE USER → ONE ACTIVE AUTHENTICATED SESSION

Un User ne peut disposer que d'une seule session authentifiée active à la fois.

Cette règle est :

**OFFICIELLE — GELÉE**

```text
ONE USER
   │
   └── ONE ACTIVE AUTHENTICATED SESSION
```

---

# 20. Nouvelle connexion

Lorsqu'un User établit une nouvelle connexion authentifiée :

1. les credentials sont vérifiés ;
2. le statut du User est vérifié ;
3. la session authentifiée existante est identifiée ;
4. toute session active précédente est révoquée ;
5. une nouvelle session est créée ;
6. la connexion est enregistrée dans Login History.

Flux :

```text
Login
 │
 ▼
Authenticate
 │
 ▼
Validate User
 │
 ▼
Revoke Previous Active Session
 │
 ▼
Create New Session
 │
 ▼
Record Login History
 │
 ▼
Authenticated
```

---

# 21. Nouvelle connexion depuis un autre appareil

Une nouvelle connexion depuis un autre appareil révoque la session précédente.

Exemple :

```text
User A

PC
└── Session 1 → ACTIVE

        ↓

Login depuis téléphone

PC
└── Session 1 → REVOKED

Téléphone
└── Session 2 → ACTIVE
```

Le système ne doit jamais conserver les deux sessions comme actives simultanément.

---

# 22. Nouvelle connexion depuis un autre navigateur

Le navigateur ne constitue pas une exception.

Exemple :

```text
Chrome
└── Session 1 → ACTIVE

        ↓

Firefox
└── Login

Chrome
└── Session 1 → REVOKED

Firefox
└── Session 2 → ACTIVE
```

---

# 23. Adresse IP et réseau

Le changement d'adresse IP ou de réseau ne permet pas de conserver plusieurs sessions actives.

La règle reste :

```text
ONE USER → ONE ACTIVE AUTHENTICATED SESSION
```

Elle s'applique indépendamment de :

* l'adresse IP ;
* Wi-Fi ;
* réseau mobile ;
* VPN ;
* localisation.

---

# 24. Connexions concurrentes

Le système doit empêcher qu'une course entre deux connexions produise plusieurs sessions actives.

Exemple interdit :

```text
User A
├── Session 1 → ACTIVE
└── Session 2 → ACTIVE
```

Résultat attendu :

```text
User A
└── Session finale → ACTIVE
```

Les autres sessions doivent être révoquées.

Cette règle doit être couverte par des tests automatisés.

---

# 25. Déconnexion

Lorsqu'un User se déconnecte :

```text
ACTIVE SESSION
      │
      ▼
Logout
      │
      ▼
REVOKED
```

La déconnexion ne supprime pas :

* le User ;
* l'historique ;
* les données d'audit.

---

# 26. Changement de mot de passe

Un changement de mot de passe doit entraîner l'invalidation de la session conformément aux règles de sécurité Identity.

Une nouvelle authentification est nécessaire pour établir une nouvelle session.

Cette mesure limite le risque lié à une session potentiellement compromise.

---

# 27. Changement de statut

Lorsqu'un User passe à un statut empêchant l'authentification, sa session active doit être invalidée conformément aux règles Identity.

Exemple :

```text
active
  │
  ▼
suspended
  │
  ▼
Active Session → REVOKED
```

---

# 28. API Tokens

Un User peut disposer d'API Tokens lorsque les fonctionnalités et permissions l'autorisent.

Les API Tokens sont indépendants des sessions web.

La règle :

```text
ONE USER → ONE ACTIVE AUTHENTICATED SESSION
```

ne signifie pas :

```text
ONE USER → ONE TOKEN
```

Le nombre et le cycle de vie des API Tokens sont définis dans :

```text
TOKEN_STANDARD.md
API_TOKEN_SPECIFICATION.md
```

---

# 29. Login History

Les authentifications du User doivent être enregistrées.

Les informations peuvent comprendre :

* User ;
* session ;
* date ;
* résultat ;
* adresse IP ;
* navigateur ;
* système d'exploitation ;
* appareil ;
* contexte de connexion.

Une nouvelle connexion entraînant la révocation d'une session précédente doit être traçable.

---

# 30. Browser Tracking

Le système peut enregistrer le contexte du navigateur utilisé lors de l'authentification.

Informations possibles :

* navigateur ;
* version ;
* système d'exploitation ;
* appareil ;
* User-Agent.

Le Browser Tracking est une information de contexte et ne modifie pas la règle de session unique.

---

# 32. Sécurité

Les données du User doivent respecter les règles de sécurité MAHLINE.

Le système doit notamment garantir :

* hash sécurisé des mots de passe ;
* absence de mot de passe en clair ;
* sessions sécurisées ;
* session fixation protection ;
* session unique ;
* révocation automatique des anciennes sessions ;
* traçabilité des connexions ;
* protection des tokens ;
* contrôle du statut ;
* audit des opérations sensibles.

---

# 33. Modèle Eloquent

Le modèle `User` doit :

* étendre `BaseModel` ;
* utiliser les ULID ;
* utiliser les timestamps ;
* utiliser Soft Deletes ;
* utiliser `HasFactory` ;
* implémenter les contrats nécessaires à l'authentification ;
* définir les casts appropriés ;
* masquer les données sensibles ;
* définir les relations Identity.

Le modèle doit rester responsable de la représentation du User et ne doit pas contenir toute la logique Authentication.

---

# 34. Factory

Le User possède une Factory dédiée.

La Factory doit :

* générer un ULID ;
* générer les champs obligatoires ;
* générer des e-mails uniques ;
* utiliser `active` par défaut ;
* utiliser `fr` comme locale ;
* utiliser `UTC` comme timezone ;
* générer un mot de passe correctement hashé lors de la persistance ;
* ne pas générer automatiquement les acteurs d'audit ;
* ne pas générer de suppression logique par défaut.

La spécification est définie dans :

```text
USER_FACTORY_SPECIFICATION.md
```

---

# 37. Règles gelées

Les règles suivantes sont officielles :

### USER-R01

Le User utilise un ULID de 26 caractères comme identifiant primaire.

### USER-R02

L'e-mail est unique.

### USER-R03

Le mot de passe est toujours stocké sous forme de hash.

### USER-R04

Un User supprimé logiquement ne peut pas s'authentifier.

### USER-R05

Le statut du User contrôle son éligibilité à l'authentification.

### USER-R06

Les opérations sensibles sont auditables.

### USER-R07

Le User utilise la suppression logique lorsque la conservation historique est requise.

### USER-R08

## ONE USER → ONE ACTIVE AUTHENTICATED SESSION

Un User ne peut avoir qu'une seule session authentifiée active.

### USER-R09

Toute nouvelle authentification valide révoque automatiquement la session authentifiée active précédente.

### USER-R10

La règle de session unique est indépendante du navigateur, de l'appareil, du système d'exploitation, de l'adresse IP et du réseau.

### USER-R11

Les API Tokens sont séparés des sessions authentifiées.

# 40. Statut final

**USER_SPECIFICATION.md — OFFICIEL — GELÉ**

La règle fondamentale de session du User est :

```text
ONE USER
   │
   └── ONE ACTIVE AUTHENTICATED SESSION
```

Une nouvelle authentification valide remplace automatiquement la session authentifiée active précédente.

Cette règle est obligatoire pour toute implémentation MAHLINE du domaine Identity.

Toute modification permettant plusieurs sessions authentifiées simultanément devra faire l'objet d'une nouvelle décision d'architecture et d'une nouvelle version de cette spécification.
