# ID-001.6 — AUTHENTICATION_SPECIFICATION

## MAHLINE Framework

### Domaine

Identity

### Composant

Authentication

### Référence

ID-001.6

### Version

1.0

### Statut

OFFICIEL — GELÉ

---

# 1. Objectif

Ce document définit les spécifications fonctionnelles du mécanisme d'authentification du framework MAHLINE.

L'authentification permet de vérifier l'identité d'un utilisateur avant de lui accorder l'accès aux ressources protégées du système.

L'authentification constitue un composant central du domaine **Identity**.

Elle travaille notamment avec :

* User ;
* UserStatus ;
* Session ;
* Login History ;
* Browser Tracking ;
* API Token ;
* Role & Permission ;
* Audit.

---

# 2. Responsabilités

Le composant Authentication est responsable de :

* vérifier les identifiants ;
* authentifier un utilisateur ;
* vérifier le statut du compte ;
* vérifier les restrictions d'accès ;
* créer une session après authentification réussie ;
* journaliser les tentatives de connexion ;
* gérer `Remember Me` ;
* déclencher la vérification d'adresse e-mail lorsque nécessaire ;
* gérer les échecs d'authentification ;
* appliquer les protections contre les tentatives répétées ;
* permettre la déconnexion ;
* permettre la révocation d'une session ;
* invalider les sessions conformément aux règles de sécurité.

---

# 3. Méthodes d'authentification

MAHLINE supporte initialement :

1. E-mail + mot de passe ;
2. API Token.

Les méthodes suivantes sont prévues pour une évolution future :

* MFA ;
* OAuth2 ;
* OpenID Connect ;
* SSO ;
* WebAuthn ;
* Passkeys ;
* authentification sociale.

Ces extensions ne doivent pas remettre en cause l'architecture existante.

---

# 4. Authentification par e-mail et mot de passe

L'utilisateur fournit :

* adresse e-mail ;
* mot de passe.

Le système doit :

1. rechercher l'utilisateur par e-mail ;
2. vérifier l'existence du compte ;
3. vérifier son statut ;
4. vérifier le mot de passe ;
5. vérifier les restrictions de sécurité ;
6. enregistrer la tentative ;
7. créer une session en cas de succès ;
8. journaliser la connexion.

---

# 5. Identifiant d'authentification

L'adresse e-mail constitue l'identifiant principal de l'authentification utilisateur.

L'adresse e-mail doit être :

* unique ;
* normalisée selon les règles du framework ;
* associée à un seul User.

Le téléphone ne constitue pas l'identifiant d'authentification initial.

Une authentification par téléphone pourra être ajoutée ultérieurement.

---

# 6. Mot de passe

Les mots de passe :

* sont obligatoires pour l'authentification par mot de passe ;
* sont toujours stockés sous forme de hash ;
* ne sont jamais stockés en clair ;
* ne sont jamais enregistrés dans les logs ;
* ne sont jamais retournés dans les réponses API.

Le système utilise les mécanismes de hachage supportés par Laravel.

La politique détaillée des mots de passe est définie dans :

```text
PASSWORD_STANDARD.md
```

---

# 7. Statut du compte

Le statut du User doit être vérifié avant toute authentification.

Les statuts sont définis par :

```text
UserStatus
```

Valeurs actuellement supportées :

* active ;
* inactive ;
* suspended ;
* pending ;
* archived.

---

# 8. Règles selon le statut

### active

L'utilisateur peut s'authentifier normalement si toutes les autres conditions sont satisfaites.

### inactive

L'authentification est refusée.

### suspended

L'authentification est refusée.

### pending

L'authentification est refusée tant que les conditions de validation du compte ne sont pas satisfaites.

### archived

L'authentification est refusée.

Aucun statut non défini par `UserStatus` ne doit être accepté.

---

# 9. Vérification de l'adresse e-mail

L'adresse e-mail peut nécessiter une vérification avant l'accès aux ressources protégées.

La vérification est effectuée à l'aide du mécanisme de vérification d'e-mail de MAHLINE.

Une adresse non vérifiée ne doit pas automatiquement être considérée comme un compte inexistant.

La politique exacte dépend du type de compte et des règles métier applicables.

---

# 10. Échec d'authentification

Lorsqu'une authentification échoue :

* aucune session authentifiée ne doit être créée ;
* l'échec doit être journalisé ;
* aucun mot de passe ne doit être enregistré ;
* aucune information sensible ne doit être retournée.

Le message retourné doit éviter de révéler inutilement si :

* l'e-mail existe ;
* le compte est inexistant ;
* le mot de passe est incorrect.

Le système doit utiliser une réponse d'authentification générique lorsque cela est nécessaire pour éviter l'énumération des comptes.

---

# 11. Tentatives multiples

Le système doit protéger l'authentification contre les tentatives répétées.

Les mécanismes prévus comprennent :

* rate limiting ;
* limitation du nombre de tentatives ;
* verrouillage temporaire ;
* journalisation des tentatives ;
* surveillance des comportements suspects.

Les seuils exacts seront définis dans les standards de sécurité du framework.

---

# 12. Authentification réussie

Après authentification réussie :

1. le User est identifié ;
2. le statut est validé ;
3. le mot de passe est validé ;
4. la session est créée ou renouvelée ;
5. les informations du navigateur sont enregistrées ;
6. l'adresse IP est enregistrée ;
7. la connexion est journalisée ;
8. les événements de sécurité éventuels sont déclenchés.

---

# 13. Session

Chaque authentification web réussie doit être associée à une session.

La session doit permettre de conserver au minimum :

* utilisateur ;
* identifiant de session ;
* adresse IP ;
* navigateur ;
* système d'exploitation ;
* appareil ;
* date de connexion ;
* date de dernière activité.

Les règles détaillées sont définies dans :

```text
SESSION_SPECIFICATION.md
```

---

# 14. Session Fixation

Après une authentification réussie, l'identifiant de session doit être renouvelé afin de prévenir les attaques de session fixation.

L'ancien identifiant de session ne doit plus être utilisable comme session authentifiée.

---

# 15. Remember Me

MAHLINE supporte le mécanisme `Remember Me`.

Lorsque l'utilisateur sélectionne cette option :

* une authentification persistante peut être maintenue ;
* le mécanisme doit respecter les règles de sécurité du framework ;
* le token associé ne doit jamais être exposé ;
* la révocation doit être possible.

---

# 16. Navigateurs

Chaque session doit identifier le navigateur utilisé.

Les informations peuvent notamment comprendre :

* User-Agent ;
* navigateur ;
* version ;
* système d'exploitation ;
* appareil.

Les règles détaillées sont définies dans :

```text
BROWSER_TRACKING_STANDARD.md
```

---

# 17. Connexions simultanées

MAHLINE autorise plusieurs sessions simultanées.

Plusieurs navigateurs peuvent donc être connectés au même compte.

Cependant, lorsque deux connexions concurrentes sont détectées depuis le même navigateur pour un même utilisateur, la politique de sécurité MAHLINE peut invalider la session précédente.

Cette règle est implémentée dans le domaine Identity.

---

# 18. Journal des connexions

Chaque tentative d'authentification doit être journalisée.

Le journal doit distinguer :

* succès ;
* échec.

Les informations enregistrées peuvent comprendre :

* utilisateur ;
* date et heure ;
* adresse IP ;
* navigateur ;
* système d'exploitation ;
* appareil ;
* session ;
* résultat ;
* raison technique de l'échec lorsque cela est nécessaire ;
* API Token utilisé, si applicable.

Le mot de passe ne doit jamais être journalisé.

Les règles détaillées sont définies dans :

```text
LOGIN_HISTORY_STANDARD.md
```

---

# 19. Authentification par API Token

Les API peuvent utiliser un token d'authentification.

Le processus est :

1. réception du token ;
2. recherche du token ;
3. vérification de sa validité ;
4. vérification de sa révocation ;
5. vérification de son expiration ;
6. identification du User ;
7. vérification du statut du User ;
8. vérification des permissions ;
9. journalisation ;
10. autorisation de la requête.

Les règles détaillées sont définies dans :

```text
API_TOKEN_SPECIFICATION.md
TOKEN_STANDARD.md
```

et :

```text
API_TOKEN_SPECIFICATION.md
```

---

# 20. Révocation

Une session authentifiée doit pouvoir être révoquée.

La révocation peut être déclenchée par :

* l'utilisateur ;
* un administrateur autorisé ;
* une modification de sécurité ;
* un changement de mot de passe ;
* une détection de sécurité ;
* l'expiration de la session.

Après révocation, la session ne doit plus permettre l'accès authentifié.

---

# 21. Changement du mot de passe

Lorsqu'un utilisateur change son mot de passe :

* l'ancien mot de passe devient invalide ;
* le nouveau mot de passe est haché ;
* les sessions actives sont invalidées conformément à la politique de sécurité ;
* l'événement est journalisé ;
* une notification peut être envoyée.

---

# 22. Déconnexion

La déconnexion doit :

* invalider la session courante ;
* supprimer les informations d'authentification persistantes lorsque nécessaire ;
* enregistrer l'événement de sécurité si la politique le prévoit.

La déconnexion ne doit pas supprimer l'utilisateur.

---

# 23. Authentification et autorisation

L'authentification et l'autorisation sont deux responsabilités distinctes.

### Authentication

Répond à :

> Qui est l'utilisateur ?

### Authorization

Répond à :

> Que cet utilisateur a-t-il le droit de faire ?

Les rôles et permissions ne doivent donc pas être implémentés directement dans le mécanisme d'authentification.

L'autorisation est définie dans :

```text
ROLE_PERMISSION_STANDARD.md
```

---

# 24. Administrateur et Super Administrateur

Le statut d'administrateur n'est pas déterminé par :

```text
UserStatus
```

`UserStatus` décrit l'état du compte.

Le rôle détermine les privilèges.

Exemple :

```text
UserStatus = active
Role = Super Administrator
```

L'utilisateur est actif et possède les privilèges du rôle Super Administrator.

Autre exemple :

```text
UserStatus = active
Role = Administrator
```

L'utilisateur est actif et possède les privilèges du rôle Administrator.

Le mécanisme d'authentification ne doit donc pas déterminer les privilèges à partir d'un champ `is_admin` ou `is_super_admin`.

L'authentification vérifie :

```text
Identité + Statut + Credentials
```

L'autorisation vérifie :

```text
User + Roles + Permissions
```

---

# 25. Audit

Les événements sensibles d'authentification doivent être auditables.

Les événements comprennent notamment :

* authentification réussie ;
* authentification échouée ;
* déconnexion ;
* changement de mot de passe ;
* révocation de session ;
* révocation de token ;
* verrouillage du compte ;
* déverrouillage du compte.

Les règles générales sont définies dans :

```text
AUDIT_STANDARD.md
```

---

# 26. Protection des données sensibles

Les informations suivantes ne doivent jamais apparaître dans les logs :

* mot de passe ;
* token complet ;
* cookie de session ;
* secret cryptographique ;
* données d'authentification sensibles.

Lorsqu'un token doit être identifié dans un journal, seule une représentation sécurisée ou une empreinte appropriée doit être utilisée.

---

# 27. Réponses d'authentification

Une réponse d'authentification réussie peut contenir :

* identité publique de l'utilisateur ;
* informations nécessaires à la session ;
* token API lorsqu'une authentification API le requiert.

Une réponse ne doit jamais contenir :

* mot de passe ;
* hash du mot de passe ;
* remember token ;
* secrets internes ;
* données d'audit sensibles.

---

# 28. Architecture technique

Le composant Authentication respecte l'architecture MAHLINE :

```text
Identity
│
├── Users
├── Authentication
├── Sessions
├── Tokens
├── Login History
├── Browser Tracking
└── Roles & Permissions
```

Le composant Authentication ne doit pas dépendre directement d'un contrôleur HTTP.

La logique métier doit être réutilisable depuis :

* Web ;
* API ;
* CLI ;
* Jobs ;
* Tests.

---

# 29. Services

Les services d'authentification doivent respecter les conventions MAHLINE.

Ils ne doivent pas dépendre directement de :

```php
Illuminate\Http\Request
```

Les données HTTP doivent être récupérées à la couche appropriée puis transmises au domaine sous forme de données structurées.

---

# 30. Actions

Les opérations importantes peuvent être représentées par des Actions dédiées :

* `AuthenticateUser`
* `LogoutUser`
* `RevokeSession`
* `ChangePassword`
* `VerifyUserEmail`

Les noms définitifs doivent respecter les conventions de nommage MAHLINE.

---

# 31. Exceptions

Les erreurs d'authentification doivent utiliser des exceptions adaptées au domaine lorsque cela est nécessaire.

Les catégories peuvent notamment comprendre :

* invalid credentials ;
* account inactive ;
* account suspended ;
* account pending ;
* account archived ;
* session revoked ;
* token invalid ;
* token expired ;
* authentication rate limited.

Les exceptions ne doivent jamais exposer de données sensibles.

# 33. Règles métier principales

Les règles suivantes sont obligatoires :

1. Un utilisateur doit exister pour être authentifié.
2. Le compte doit posséder un statut autorisant l'authentification.
3. Le mot de passe doit être valide pour une authentification par mot de passe.
4. Une authentification réussie crée une session web.
5. Une authentification réussie est journalisée.
6. Une authentification échouée est journalisée.
7. Un mot de passe ne doit jamais être journalisé.
8. Une session révoquée ne peut plus être utilisée.
9. Un token révoqué ne peut plus être utilisé.
10. Un token expiré ne peut plus être utilisé.
11. Le changement de mot de passe doit invalider les sessions conformément à la politique de sécurité.
12. L'authentification ne détermine pas les rôles.
13. L'autorisation est gérée séparément.
14. Les comptes `suspended` et `archived` ne peuvent pas s'authentifier.

# Conclusion

Le composant **Authentication** constitue le mécanisme permettant à MAHLINE de vérifier l'identité d'un User et d'établir une session ou une authentification API.

Il est volontairement séparé de l'autorisation.

Le statut du compte détermine si l'utilisateur peut s'authentifier, tandis que les rôles et permissions déterminent ce qu'il peut faire après authentification.

Cette séparation constitue une règle architecturale fondamentale du domaine **Identity**.
