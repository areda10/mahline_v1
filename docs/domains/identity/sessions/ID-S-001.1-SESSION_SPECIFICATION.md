# SESSION_SPECIFICATION

## MAHLINE Framework

### Domaine

Identity

### Composant

Session

### Référence

ID-001.7

### Version

1.0

### Statut

OFFICIEL — GELÉ

---

# 1. Objectif

Ce document définit les spécifications fonctionnelles du mécanisme de gestion des sessions du framework MAHLINE.

Une session représente l'état d'authentification d'un utilisateur pendant une période donnée.

La session permet au système de reconnaître un utilisateur authentifié sans lui demander de fournir ses identifiants à chaque requête.

---

# 2. Responsabilités

Le composant Session est responsable de :

* créer une session après authentification réussie ;
* identifier l'utilisateur associé à une session ;
* maintenir l'état d'authentification ;
* enregistrer les informations techniques de connexion ;
* suivre l'activité de la session ;
* gérer l'expiration ;
* révoquer une session ;
* détruire une session ;
* gérer les sessions simultanées ;
* appliquer les règles de sécurité liées au navigateur ;
* permettre à l'utilisateur de consulter ses sessions actives.

---

# 3. Relation avec User

Chaque session authentifiée appartient à un User.

Relation conceptuelle :

```text
User
  │
  └── hasMany Sessions
```

Une session ne peut pas être associée à plusieurs utilisateurs.

Une session doit toujours permettre d'identifier son propriétaire.

---

# 4. Création d'une session

Une session est créée après une authentification réussie.

Le processus est :

```text
Authentication
      │
      ▼
User identifié
      │
      ▼
Vérification UserStatus
      │
      ▼
Credentials valides
      │
      ▼
Création / renouvellement Session
      │
      ▼
Journalisation Login
```

Une authentification échouée ne doit pas créer de session authentifiée.

---

# 5. Identifiant de session

Chaque session possède un identifiant unique.

Le `session_id` :

* doit être unique ;
* doit être imprévisible ;
* ne doit pas contenir l'identifiant du User ;
* ne doit pas être généré à partir d'informations prévisibles ;
* doit être renouvelé lors des opérations de sécurité appropriées.

---

# 6. Session Fixation

Après authentification, l'identifiant de session doit être renouvelé.

L'ancien identifiant ne doit plus permettre d'accéder à la session authentifiée.

Cette règle protège le système contre les attaques de type Session Fixation.

---

# 7. Informations enregistrées

Une session doit pouvoir conserver au minimum :

* identifiant de session ;
* utilisateur ;
* adresse IP ;
* User-Agent ;
* navigateur ;
* système d'exploitation ;
* appareil ;
* date de création ;
* date de dernière activité ;
* date d'expiration éventuelle ;
* état de la session.

Les données doivent respecter les standards de sécurité et de confidentialité de MAHLINE.

---

# 8. Adresse IP

L'adresse IP utilisée lors de la connexion doit être enregistrée.

Le système doit pouvoir distinguer :

* IPv4 ;
* IPv6.

La longueur de stockage doit permettre de conserver une adresse IPv6 complète.

L'adresse IP ne doit pas être utilisée comme identifiant unique d'une session.

Une même adresse IP peut être utilisée par plusieurs utilisateurs.

---

# 9. User-Agent

Le User-Agent du navigateur doit être enregistré lorsqu'il est disponible.

Il permet notamment d'identifier :

* navigateur ;
* version ;
* système d'exploitation ;
* appareil.

Le User-Agent brut peut être conservé conformément à la politique de confidentialité du projet.

---

# 10. Navigateur

Le navigateur utilisé lors de la création de la session doit être identifié.

Les informations peuvent comprendre :

* nom ;
* version ;
* moteur ;
* système d'exploitation ;
* type d'appareil.

Les règles détaillées sont définies dans :

```text
BROWSER_TRACKING_STANDARD.md
```

---

# 11. Appareil

Lorsque cela est possible, la session doit être associée à un appareil logique.

Un appareil peut représenter :

* ordinateur ;
* téléphone ;
* tablette ;
* autre terminal compatible.

L'identification de l'appareil doit respecter les contraintes de sécurité et de confidentialité.

---

# 12. Date de création

Chaque session doit enregistrer sa date de création.

Cette information permet notamment :

* l'affichage des sessions actives ;
* l'analyse de sécurité ;
* l'historique des connexions ;
* l'audit.

---

# 13. Dernière activité

Une session doit enregistrer la date de sa dernière activité connue.

Cette information permet de :

* détecter les sessions inactives ;
* appliquer l'expiration ;
* afficher l'activité récente ;
* détecter certains comportements anormaux.

La fréquence exacte de mise à jour peut être optimisée afin d'éviter une écriture en base à chaque requête.

---

# 14. Expiration

Une session peut expirer automatiquement.

L'expiration peut être déclenchée par :

* durée maximale ;
* durée d'inactivité ;
* expiration du cookie ;
* politique de sécurité ;
* changement de mot de passe ;
* révocation administrative.

Une session expirée ne doit plus permettre l'accès authentifié.

---

# 15. Session active

Une session est considérée comme active lorsqu'elle :

* appartient à un User valide ;
* n'est pas révoquée ;
* n'est pas expirée ;
* respecte les règles de sécurité.

L'état actif ne doit pas être déduit uniquement de la présence d'un enregistrement en base.

---

# 16. Sessions simultanées

MAHLINE autorise plusieurs sessions simultanées pour un même User.

Exemple :

```text
User A
│
├── Chrome / Windows
├── Firefox / Windows
├── Safari / iPhone
└── Chrome / Android
```

Chaque session reste indépendante.

La connexion sur un nouvel appareil ne doit pas automatiquement déconnecter toutes les autres sessions.

---

# 17. Même navigateur

Une règle spécifique s'applique lorsque deux connexions concurrentes sont effectuées avec le même navigateur pour le même utilisateur.

Exemple :

```text
User A
│
├── Chrome / Device A → Session 1
└── Chrome / Device A → Session 2
```

Selon la politique de sécurité MAHLINE, la nouvelle authentification peut provoquer l'invalidation de la session précédente.

Cette règle doit être appliquée uniquement lorsque le système peut déterminer de manière suffisamment fiable qu'il s'agit du même contexte navigateur.

---

# 18. Révocation

Une session peut être révoquée :

* par l'utilisateur ;
* par un administrateur autorisé ;
* automatiquement par le système ;
* à la suite d'un événement de sécurité.

Après révocation :

```text
Session → REVOKED
```

La session ne doit plus être utilisable pour accéder aux ressources protégées.

---

# 19. Déconnexion

La déconnexion de l'utilisateur doit invalider la session courante.

Le processus est :

```text
Authenticated Session
        │
        ▼
Logout
        │
        ▼
Session invalidated
```

La déconnexion ne supprime pas le User.

Elle ne supprime pas non plus l'historique de connexion.

---

# 20. Déconnexion de toutes les sessions

MAHLINE doit permettre de révoquer toutes les sessions actives d'un User.

Cette opération peut être déclenchée notamment :

* par l'utilisateur ;
* après un changement de mot de passe ;
* par un administrateur ;
* lors d'un incident de sécurité.

Toutes les sessions concernées deviennent invalides.

---

# 21. Changement de mot de passe

Par défaut, un changement de mot de passe doit entraîner l'invalidation des sessions actives.

Exception :

Une politique de sécurité explicitement définie peut autoriser la conservation d'une session particulière, par exemple la session ayant effectué le changement.

Cette exception doit être explicitement implémentée et testée.

---

# 22. Session et UserStatus

L'accès par session dépend du statut actuel du User.

Si un User devient :

```text
inactive
suspended
archived
```

ses sessions authentifiées doivent être invalidées conformément à la politique de sécurité.

Un User suspendu ne doit pas pouvoir continuer à utiliser une session authentifiée active.

---

# 23. Session et autorisation

La session permet d'identifier le User.

Elle ne contient pas directement la logique métier des permissions.

Le processus est :

```text
Session
   │
   ▼
User
   │
   ▼
Roles
   │
   ▼
Permissions
```

L'authentification et l'autorisation restent séparées.

---

# 24. Session et API

Les API utilisant un API Token ne doivent pas être assimilées automatiquement à une session web.

Les deux mécanismes sont distincts :

```text
Web
User → Session

API
User → API Token
```

Un token peut néanmoins être associé à des informations de contexte de connexion lorsque la politique du domaine l'exige.

---

# 25. Sécurité du cookie de session

Les cookies de session doivent respecter les règles de sécurité du framework.

Ils doivent notamment utiliser, selon le contexte :

* `HttpOnly` ;
* `Secure` ;
* `SameSite`.

La configuration exacte dépend de l'environnement d'exécution.

Les cookies de session ne doivent jamais contenir directement :

* mot de passe ;
* token API ;
* données personnelles inutiles ;
* permissions complètes ;
* secrets internes.

---

# 26. Régénération

L'identifiant de session doit être régénéré lors des événements de sécurité appropriés.

Événements concernés notamment :

* authentification ;
* changement de privilèges ;
* changement de mot de passe ;
* récupération de compte.

La régénération doit empêcher la réutilisation d'un ancien identifiant.

---

# 27. Nettoyage

Les sessions expirées ou révoquées peuvent être nettoyées selon une politique de conservation.

Le nettoyage ne doit pas supprimer les données nécessaires :

* à l'audit ;
* à la sécurité ;
* à l'historique ;
* aux obligations réglementaires éventuelles.

La politique de conservation est définie séparément.

---

# 28. Audit

Les événements importants liés aux sessions doivent être auditables.

Événements concernés :

* création ;
* authentification ;
* déconnexion ;
* révocation ;
* expiration ;
* révocation globale ;
* détection d'une nouvelle session ;
* invalidation pour raison de sécurité.

Les données sensibles ne doivent jamais être enregistrées dans les journaux.

---

# 29. Login History

La session est liée au journal des connexions.

Une authentification réussie doit permettre d'associer :

```text
Login History
      │
      └── Session
```

Cela permet de relier une connexion à son contexte technique.

Les règles détaillées sont définies dans :

```text
LOGIN_HISTORY_STANDARD.md
```

---

# 30. Browser Tracking

Les informations relatives au navigateur doivent être gérées selon :

```text
BROWSER_TRACKING_STANDARD.md
```

La session peut référencer le contexte navigateur utilisé lors de sa création.

---

# 31. Architecture technique

Le composant Session appartient au domaine Identity.

Structure logique :

```text
Identity
│
├── Users
│
├── Authentication
│
├── Sessions
│
├── Tokens
│
├── Login History
│
├── Browser Tracking
│
└── Roles & Permissions
```

La logique métier de session ne doit pas être directement dépendante d'un contrôleur HTTP.

Elle doit être utilisable depuis :

* Web ;
* API ;
* CLI ;
* Jobs ;
* Tests.

---

# 32. Services

Les services de session ne doivent pas dépendre directement de :

```php
Illuminate\Http\Request
```

Les informations HTTP nécessaires doivent être transformées en données structurées avant d'entrer dans la logique métier.

---

# 33. Actions

Les opérations principales peuvent être représentées par des Actions :

* `CreateSession`
* `RevokeSession`
* `RevokeAllSessions`
* `LogoutUser`
* `RefreshSession`
* `ExpireSession`

Les noms définitifs doivent respecter les conventions de nommage MAHLINE.

---

# 34. Règles métier

Les règles suivantes sont obligatoires :

1. Une session appartient à un seul User.
2. Une session doit avoir un identifiant unique.
3. Une session doit être imprévisible.
4. Une session authentifiée est créée après une authentification réussie.
5. Une authentification échouée ne crée pas de session authentifiée.
6. L'identifiant de session doit être renouvelé après authentification.
7. Plusieurs sessions simultanées sont autorisées.
8. Une session révoquée ne peut plus être utilisée.
9. Une session expirée ne peut plus être utilisée.
10. Un User suspendu ne doit pas conserver un accès authentifié actif.
11. Un changement de mot de passe invalide les sessions selon la politique de sécurité.
12. La déconnexion invalide la session courante.
13. La déconnexion globale invalide toutes les sessions concernées.
14. Les données sensibles ne doivent jamais être stockées dans le cookie de session.
15. Les informations de session doivent être journalisées conformément aux standards d'audit.
16. La session ne détermine pas les permissions de l'utilisateur.

---

Le composant Session doit être couvert par des tests automatisés.

Les tests doivent couvrir au minimum :

* création d'une session ;

* identifiant unique ;
* renouvellement de l'identifiant ;
* authentification réussie ;
* authentification échouée ;
* session active ;
* session expirée ;
* session révoquée ;
* déconnexion ;
* déconnexion globale ;
* sessions simultanées ;
* même navigateur ;
* changement de mot de passe ;
* User suspendu ;
* User archivé ;
* mise à jour de la dernière activité ;
* enregistrement de l'adresse IP ;
* enregistrement du User-Agent ;
* audit ;
* nettoyage des sessions expirées.

---

# 36. Validation

Le composant Session est conforme lorsque :

* les sessions sont correctement créées ;
* chaque session est associée au bon User ;
* les sessions sont correctement invalidées ;
* les sessions expirées ne permettent plus l'accès ;
* les sessions révoquées ne permettent plus l'accès ;
* la régénération de session fonctionne ;
* les sessions simultanées respectent la politique MAHLINE ;
* le contexte navigateur est correctement enregistré ;
* les événements importants sont journalisés ;
* les tests automatisés passent.

# Conclusion

Le composant **Session** assure le maintien sécurisé de l'état d'authentification d'un utilisateur dans MAHLINE.

Il est étroitement lié à **Authentication**, **User**, **Login History** et **Browser Tracking**, tout en restant séparé du mécanisme d'autorisation.

Une session valide représente uniquement un contexte d'authentification valide. Les rôles et permissions restent déterminés indépendamment par le système d'autorisation.

Cette séparation constitue une règle architecturale fondamentale du domaine **Identity**.
