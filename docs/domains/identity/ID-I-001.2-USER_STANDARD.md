# MAHLINE — USER STANDARD

**Version:** 1.0
**Status:** GELÉ
**Domain:** Identity / Users

## 1. Purpose

This standard defines the canonical behavior of the MAHLINE `User` model and its responsibilities within the Identity domain.

## 2. User model

Canonical class:

`App\Domains\Identity\Users\Models\User`

The User model:

* extends `BaseModel`;
* uses ULID primary keys;
* uses string, non-incrementing identifiers;
* uses timestamps;
* uses soft deletes;
* implements Laravel `Authenticatable`;
* uses `HasApiTokens`;
* uses `HasAuthorization`;
* uses `HasFactory`.

## 3. Identity attributes

Supported user attributes:

* `first_name`
* `last_name`
* `display_name`
* `email`
* `telephone`
* `password`
* `status`
* `locale`
* `timezone`

Sensitive attributes hidden from serialization:

* `password`
* `remember_token`

## 4. Casts

The User model casts:

* `status` → `UserStatus`
* `email_verified_at` → datetime
* `password` → hashed
* `deleted_at` → datetime

## 5. User status

Supported statuses are defined by `UserStatus`.

Authorization behavior depends on the status.

Only an active user is considered authorized.

The following statuses are not authorized:

* pending
* inactive
* suspended
* archived

## 6. Roles and permissions

A user may have multiple roles.

Permissions can be inherited through roles.

The authorization API provides:

* `hasRole()`
* `hasAnyRole()`
* `hasPermission()`
* `hasAnyPermission()`
* `isAuthorized()`

## 7. Authentication

The Identity domain explicitly supports:

**ONE USER → MULTIPLE ACTIVE WEB SESSIONS**

A user may therefore be authenticated simultaneously from:

* Browser A
* Browser B
* Phone
* other supported Web clients

Creating a new Web session does **not** revoke previous active Web sessions.

## 8. Web sessions and API tokens

Web authentication sessions and API authentication tokens are separate mechanisms.

```text
USER
├── Web Session A
├── Web Session B
├── Web Session C
│
└── API Token A
```

API token creation does not create a Web session.

API token revocation does not revoke Web sessions.

## 9. Password

Passwords must never be stored in plain text.

Password behavior is defined by `PASSWORD_STANDARD.md`.

## 10. Factory

`UserFactory` must create valid users and:

* generate unique email addresses;
* use active status by default;
* use French locale by default;
* use UTC timezone by default;
* create verified email by default;
* hash persisted passwords;
* not create audit actors;
* not create soft-deleted users.

## 11. Validation

The User model is covered by:

* `UserTest`
* `UserPasswordTest`
* `UserFactoryTest`

## 12. Freeze rule

Any change to the User model must update:

1. the affected tests;
2. this standard;
3. the Identity test suite.

Identity cannot be considered frozen until the full suite is green.
