# PASSWORD_STANDARD.md

# MAHLINE Framework

## Password Standard

### Référence

IDENTITY / SECURITY / PASSWORD

### Version

1.0

### Statut

**OFFICIEL — GELÉ**

---

# 1. Objectif

Ce document définit les règles officielles MAHLINE concernant les mots de passe des Users.

Il couvre :

* création du mot de passe ;
* stockage ;
* vérification ;
* modification ;
* réinitialisation ;
* sécurité ;
* expiration éventuelle ;
* audit ;
* tests.

---

# 2. Principe fondamental

Le mot de passe est une donnée secrète.

```text id="a7v9q2"
PASSWORD = SECRET
```

Le mot de passe ne doit jamais être considéré comme une donnée métier ordinaire.

---

# 3. Interdiction du stockage en clair

MAHLINE ne doit jamais stocker un mot de passe en clair.

Interdit :

```text id="j3r5k8"
password = "MonMotDePasse123"
```

La base de données doit uniquement contenir une représentation sécurisée du mot de passe.

---

# 4. Hashage

Le mot de passe doit être hashé avant son stockage.

Flux :

```text id="n5t2x9"
PLAIN PASSWORD
      │
      ▼
PASSWORD HASHING
      │
      ▼
DATABASE
```

La vérification doit être effectuée avec le mécanisme de vérification du hash.

---

# 5. Algorithme

MAHLINE doit utiliser le mécanisme de hashage de mot de passe sécurisé fourni par Laravel/PHP.

L'application ne doit pas implémenter elle-même un algorithme cryptographique de hashage.

Le choix concret de l'algorithme doit rester configurable via le système de hashing Laravel.

---

# 6. Hashing lors de la création

Lorsqu'un User est créé :

```text id="d6m4p1"
User input
    │
    ▼
Validate password
    │
    ▼
Hash password
    │
    ▼
Persist User
```

Le modèle `User` ne doit jamais recevoir ou conserver inutilement le mot de passe en clair après le traitement nécessaire.

---

# 7. Hashing lors de la modification

Lorsqu'un User modifie son mot de passe :

```text id="q1s7v4"
CURRENT PASSWORD
       │
       ▼
VERIFY
       │
       ▼
NEW PASSWORD
       │
       ▼
HASH
       │
       ▼
SAVE
```

---

# 8. Vérification du mot de passe

La vérification doit utiliser le mécanisme sécurisé de comparaison de hash.

Le système ne doit jamais comparer directement :

```text id="x4n8p6"
plain_password === stored_password
```

Le système doit comparer le mot de passe fourni avec le hash stocké à l'aide du service de hashing.

---

# 9. Authentication

Le mot de passe participe à l'authentification.

Flux :

```text id="b8k2w1"
EMAIL
  +
PASSWORD
  │
  ▼
AUTHENTICATION
  │
  ├── FAILED → LOGIN FAILED
  │
  ▼
USER VALID
  │
  ▼
SESSION CREATION
```

La réussite de l'authentification ne donne pas automatiquement toutes les permissions.

L'autorisation reste distincte.

---

# 10. User Status

Un mot de passe correct ne suffit pas à authentifier un User dont le compte n'est pas autorisé à se connecter.

Exemple :

```text id="v9h3c5"
password = correct
status = suspended
```

Résultat :

```text id="z2m7k4"
ACCESS DENIED
```

Le statut User doit être vérifié conformément à :

```text id="u8f1n6"
USER_STATUS_SPECIFICATION.md
```

---

# 11. Email Verification

Lorsque l'architecture exige la vérification de l'adresse email avant connexion, le système doit vérifier :

```text id="r5k3d9"
email_verified_at
```

Un mot de passe correct ne doit pas contourner cette règle.

---

# 12. Password Validation

Un mot de passe doit être validé avant son hashage.

Les règles de validation doivent couvrir au minimum :

```text id="t7p4m2"
minimum length
confirmation
required value
```

Les règles exactes de complexité doivent rester cohérentes avec la politique de sécurité MAHLINE.

---

# 13. Longueur minimale

MAHLINE doit imposer une longueur minimale suffisamment forte pour éviter les mots de passe trivialement faibles.

Valeur recommandée :

```text id="h4q8w6"
minimum = 12 characters
```

Cette valeur constitue le standard par défaut.

Une politique plus stricte peut être appliquée par environnement ou selon le niveau de sécurité requis.

---

# 14. Complexité

MAHLINE ne doit pas dépendre exclusivement de règles artificielles telles que :

```text id="c7x2m9"
1 uppercase
1 lowercase
1 number
1 special character
```

La longueur et l'imprévisibilité du mot de passe sont prioritaires.

Les mots de passe connus comme compromis ou extrêmement faibles doivent être rejetés lorsque le mécanisme approprié est disponible.

---

# 15. Password Confirmation

Les opérations suivantes doivent généralement demander une confirmation :

```text id="w6k3p2"
password creation
password change
password reset
```

La confirmation ne doit jamais être stockée.

---

# 16. Password Confirmation Storage

Interdit :

```text id="q9m4t7"
password_confirmation
```

dans la base de données.

Interdit également dans :

```text id="v2n8s5"
audit
logs
events
exceptions
```

---

# 17. Password Hash Storage

Le champ :

```text id="p3f7k1"
password
```

contient uniquement le hash.

Exemple conceptuel :

```text id="m8d2r6"
password = "$2y$..."
```

ou une représentation correspondant à l'algorithme configuré.

---

# 18. Password Access

Le hash du mot de passe ne doit pas être exposé inutilement.

Les réponses API et ressources User ne doivent pas retourner :

```text id="b6h1x9"
password
```

---

# 19. User Model

Le modèle `User` doit masquer le mot de passe lors de la sérialisation.

Exemple :

```php id="c5r9m3"
protected $hidden = [
    'password',
    'remember_token',
];
```

Le modèle peut également utiliser les casts Laravel appropriés pour le champ password.

---

# 20. Password Change

Une modification de mot de passe doit suivre :

```text id="d4k7s2"
REQUEST
  │
  ▼
AUTHENTICATE USER
  │
  ▼
VERIFY CURRENT PASSWORD
  │
  ▼
VALIDATE NEW PASSWORD
  │
  ▼
HASH NEW PASSWORD
  │
  ▼
SAVE
  │
  ▼
AUDIT
```

---

# 21. Current Password

Lorsque le User est déjà authentifié et demande une modification de mot de passe, le système doit demander son mot de passe actuel lorsque la politique de sécurité l'exige.

Cela permet de limiter les modifications accidentelles ou abusives.

---

# 22. Password Reset

La réinitialisation du mot de passe est distincte de la modification normale.

Flux :

```text id="n3v8q5"
RESET REQUEST
      │
      ▼
RESET TOKEN
      │
      ▼
VERIFY TOKEN
      │
      ▼
NEW PASSWORD
      │
      ▼
HASH
      │
      ▼
SAVE
```

---

# 23. Reset Token

Le token de réinitialisation ne doit jamais être traité comme un mot de passe.

Il doit être :

```text id="s7k2m4"
temporary
single-use
time-limited
secret
```

Son secret ne doit jamais être écrit dans les logs ou l'audit.

---

# 24. Password Reset Expiration

Un token de réinitialisation doit expirer après une durée limitée.

Le système doit utiliser la configuration Laravel appropriée.

---

# 25. Password Reset Invalidation

Après une réinitialisation réussie :

```text id="p8d4x6"
RESET TOKEN
      │
      ▼
CONSUMED
      │
      ▼
INVALID
```

Le même token ne doit pas pouvoir être réutilisé.

---

# 26. Session après changement de mot de passe

Un changement de mot de passe est une opération de sécurité.

Selon la politique d'authentification MAHLINE, les sessions authentifiées existantes peuvent être invalidées.

La politique finale doit rester cohérente avec :

```text id="q6w9k3"
ONE USER → ONE ACTIVE AUTHENTICATED SESSION
```

Après changement de mot de passe, une nouvelle authentification peut être exigée.

---

# 27. API Tokens après changement de mot de passe

Les API Tokens sont indépendants des sessions Web.

Un changement de mot de passe ne doit pas automatiquement être interprété comme une révocation de tous les API Tokens.

Cependant, lors d'un incident de sécurité, MAHLINE doit permettre :

```text id="f4n7c2"
REVOKE ALL API TOKENS
```

---

# 28. Password Compromise

Si un mot de passe est considéré comme compromis :

```text id="x8m5q1"
FORCE PASSWORD RESET
```

peut être appliqué.

Les sessions actives doivent être traitées conformément à la politique de sécurité.

---

# 29. Password Reuse

MAHLINE peut empêcher la réutilisation récente des mots de passe.

Si cette fonctionnalité est activée, elle doit être documentée et testée.

Les anciens mots de passe doivent également rester sous forme de hash et ne doivent jamais être récupérables.

---

# 30. Password Expiration

MAHLINE ne doit pas imposer automatiquement une expiration périodique arbitraire des mots de passe uniquement pour respecter une règle de calendrier.

Une expiration peut être imposée lorsque :

```text id="m1r6v8"
security incident
compromise
administrative policy
regulatory requirement
```

le justifie.

---

# 31. Password Strength

La force du mot de passe doit être évaluée avant stockage.

Les mots de passe extrêmement faibles doivent être rejetés.

Exemples à refuser :

```text id="r4p8n2"
password
123456789012
azerty
qwerty
```

---

# 32. Password Dictionary

Lorsque cela est possible, MAHLINE peut utiliser une liste de mots de passe compromis ou extrêmement courants.

Cette vérification doit être effectuée avant le hashage.

---

# 33. Password Logging

Interdit :

```text id="g7m3k9"
Log::info($password);
```

Interdit également :

```text id="d2x8q4"
Log::debug([
    'password' => $password,
]);
```

---

# 34. Password Audit

L'audit peut enregistrer :

```text id="v5n1s7"
PASSWORD_CHANGED
PASSWORD_RESET
PASSWORD_RESET_REQUESTED
PASSWORD_COMPROMISED
```

mais jamais le mot de passe.

---

# 35. Password Audit Data

Autorisé :

```text id="q8k4m2"
actor_id
user_id
timestamp
event
reason
```

Interdit :

```text id="z6p3w9"
password
password_confirmation
password_hash
reset_secret
```

---

# 36. Authentication Failure

Lorsqu'un mot de passe incorrect est fourni, le système doit produire une réponse générique.

Éviter de révéler :

```text id="h2r7m5"
email exists
password incorrect
account exists
```

La réponse doit limiter les possibilités d'énumération des comptes.

---

# 37. Rate Limiting

Les tentatives d'authentification doivent être protégées contre le brute-force.

Le système peut appliquer :

```text id="s9c4n6"
rate limiting
throttling
temporary lockout
abuse detection
```

selon la politique de sécurité retenue.

---

# 38. Brute Force

Le système doit pouvoir détecter des séries de tentatives anormales.

Les mesures exactes doivent être centralisées dans le mécanisme Authentication/Security et non dans le modèle `User`.

---

# 39. Password Service

La logique de mot de passe doit être centralisée dans un service approprié.

Exemple :

```text id="u3k8q5"
app/Core/Security/Services/PasswordService.php
```

ou dans le domaine Identity selon l'architecture finale.

Le service ne doit pas dépendre directement de `Request`.

---

# 40. Responsabilité du PasswordService

Le service peut être responsable de :

```text id="m7p2x9"
hash
verify
validate policy
generate reset data
```

Il ne doit pas être responsable de :

```text id="a4n8k1"
HTTP request
controller response
session UI
database migration
```

---

# 41. PasswordService Tests

Les tests doivent vérifier au minimum :

```text id="k6d3r8"
✓ password can be hashed
✓ hash is different from plain password
✓ valid password verifies
✓ invalid password fails
✓ empty password is rejected
✓ weak password is rejected
✓ confirmation mismatch is rejected
✓ password is never returned in User serialization
✓ password is never written to audit
✓ password is never written to logs
```

---

# 42. User Factory

La Factory User doit utiliser une valeur de mot de passe adaptée aux tests.

Elle ne doit jamais utiliser un mot de passe réel.

Exemple :

```text id="w5q9m2"
password = test password
```

Le mot de passe doit néanmoins être hashé lorsqu'un User est persisté.

---

# 43. Tests Factory

`UserFactoryTest.php` doit vérifier notamment :

```text id="r8v4c6"
✓ factory creates user
✓ password exists
✓ password is hashed
✓ plain password is not stored
```

---

# 44. Database

Le champ User :

```text id="n2x7p5"
password
```

doit être suffisamment dimensionné pour stocker le hash produit par l'algorithme configuré.

Le champ ne doit pas être limité à une taille arbitrairement faible.

---

# 45. Migration User

La migration User doit respecter :

```text id="q4m8s1"
password
```

comme champ obligatoire.

Le champ ne doit pas être nullable pour un User authentifiable par mot de passe.

---

# 46. Password et API Token

Un API Token ne doit jamais être utilisé comme substitut du password dans le processus de connexion Web.

```text id="f7k3d9"
PASSWORD
   ↓
WEB AUTHENTICATION

API TOKEN
   ↓
API AUTHENTICATION
```

---

# 47. Password et Session

La réussite d'une authentification par password peut créer une session.

MAHLINE impose :

```text id="p9w2x6"
ONE USER
   ↓
ONE ACTIVE AUTHENTICATED SESSION
```

Lors d'une nouvelle authentification Web réussie :

```text id="c3n7m5"
NEW LOGIN
    ↓
INVALIDATE PREVIOUS ACTIVE SESSION
    ↓
CREATE NEW ACTIVE SESSION
```

---

# 48. Password et Browser Tracking

Le contexte navigateur d'une authentification peut être conservé conformément à :

```text id="v8k4q2"
BROWSER_TRACKING_STANDARD.md
```

Le navigateur ne constitue cependant pas le secret d'authentification.

---

# 49. Password et Login History

Les opérations liées au mot de passe peuvent générer des événements dans :

```text id="m5r9d3"
LOGIN_HISTORY
```

ou dans le mécanisme de sécurité approprié.

Exemples :

```text id="x1q7k4"
LOGIN_SUCCESS
LOGIN_FAILED
PASSWORD_RESET
```

---

# 50. Password et Audit

Les changements de mot de passe doivent être auditables :

```text id="h8s3p6"
PASSWORD_CHANGED
PASSWORD_RESET
```

mais jamais avec le secret.

Référence :

```text id="a2m7w5"
AUDIT_STANDARD.md
```

---

# 51. Séparation des responsabilités

Le système doit respecter :

```text id="n6q4x8"
PASSWORD
    │
    ▼
PASSWORD SERVICE
    │
    ▼
AUTHENTICATION SERVICE
    │
    ▼
SESSION SERVICE
    │
    ▼
LOGIN HISTORY / AUDIT
```

Chaque composant conserve sa responsabilité.

---

# 52. Invariants

### PASSWORD-001

Le mot de passe est toujours considéré comme un secret.

### PASSWORD-002

Le mot de passe ne doit jamais être stocké en clair.

### PASSWORD-003

Le mot de passe ne doit jamais apparaître dans les logs.

### PASSWORD-004

Le mot de passe ne doit jamais apparaître dans l'audit.

### PASSWORD-005

Le `password_confirmation` ne doit jamais être persisté.

### PASSWORD-006

Un mot de passe correct ne contourne jamais le `User.status`.

### PASSWORD-007

Un User supprimé ou désactivé ne doit pas pouvoir s'authentifier.

### PASSWORD-008

La vérification doit utiliser le mécanisme sécurisé de hashing.

### PASSWORD-009

Le changement de mot de passe doit être auditable.

### PASSWORD-010

La réinitialisation doit utiliser un mécanisme temporaire et sécurisé.

### PASSWORD-011

Les reset tokens ne doivent jamais être enregistrés dans les logs.

### PASSWORD-012

Une nouvelle authentification respecte :

```text id="w7c2m9"
ONE USER → ONE ACTIVE AUTHENTICATED SESSION
```

### PASSWORD-013

Les API Tokens restent indépendants des sessions Web.

### PASSWORD-014

Le PasswordService ne dépend pas de `Request`.

# 56. Règles de sécurité gelées

MAHLINE retient définitivement :

```text id="m3x7q8"
PASSWORD = SECRET
```

```text id="v6n2p4"
NO PLAINTEXT PASSWORD STORAGE
```

```text id="z8k4r1"
NO PASSWORD IN LOGS
```

```text id="s5q9m3"
NO PASSWORD IN AUDIT
```

et :

```text id="h7c2w6"
ONE USER → ONE ACTIVE AUTHENTICATED SESSION
```

pour l'authentification Web.

Les API Tokens restent indépendants :

```text id="p4m8x2"
ONE USER → MANY API TOKENS
```
