# 1. Purpose

This document defines the official specification for the `SoftDeleteMacros` component of the MAHLINE Framework.

`SoftDeleteMacros` provides reusable Laravel Blueprint macros for standardized soft-delete column definitions.

Its objectives are to:

* centralize soft-delete column creation;
* enforce MAHLINE soft-delete conventions;
* maintain consistency across database tables;
* avoid duplicated `deleted_at` definitions;
* keep soft-delete concerns separate from audit columns.

# 3. Responsibilities

`SoftDeleteMacros` is responsible for:

* registering soft-delete Blueprint macros;
* creating the standardized `deleted_at` column;
* supporting configurable timestamp precision;
* providing a complete soft-delete definition where required.

It must not:

* create `deleted_by`;
* create audit columns;
* create indexes;
* create foreign keys;
* contain business logic;
* modify Eloquent model behavior.

# 6. Official V1 Macros

## 6.1 softDelete()

Creates the standard MAHLINE soft-delete column.

```php
$table->softDelete();
```

Generated column:

```text
deleted_at
```

Type:

```text
timestamp
```

Nullable:

```text
Yes
```

---

# 7. softDelete() Behavior

The generated column must:

* be nullable;
* default to `NULL`;
* contain no foreign key;
* contain no automatic index unless explicitly configured.

The macro represents the database column only.

It does not enable Laravel's `SoftDeletes` trait.

---

# 8. Optional Precision

The macro may support an optional precision parameter.

Example:

```php
$table->softDelete(6);
```

This creates a timestamp with microsecond precision where supported by the database engine.

The default precision is defined by:

```php
config('database_macros.soft_deletes.precision')
```

---

# 9. softDeletes()

For consistency with Laravel terminology, the framework may expose:

```php
$table->softDeletes();
```

as an alias of:

```php
$table->softDelete();
```

The canonical MAHLINE API is:

```php
$table->softDelete();
```

The plural alias exists only for Laravel familiarity and compatibility.

---

# 10. Soft Delete and Audit Separation

Soft delete and audit are separate concepts.

Soft delete:

```text
deleted_at
```

Audit:

```text
created_by
updated_by
deleted_by
```

Therefore:

```php
$table->softDelete();
```

must not automatically create:

```text
deleted_by
```

Likewise:

```php
$table->auditColumns();
```

must not automatically create:

```text
deleted_at
```

---

# 11. Complete Example

A standard MAHLINE business table may use:

```php
Schema::create('products', function (Blueprint $table) {
    $table->ulidPrimary();

    $table->status();

    $table->auditColumns();

    $table->auditIndexes();

    $table->softDelete();
});
```

This produces conceptually:

```text
id
status
created_by
updated_by
deleted_by
created_at
updated_at
deleted_at
```

---

# 12. Indexing Rules

`SoftDeleteMacros` must not automatically create an index on `deleted_at`.

Indexing `deleted_at` is a database-design decision and must be handled explicitly.

Example:

```php
$table->softDelete();

$table->indexColumns([
    'deleted_at',
]);
```

---

# 13. Foreign Key Rules

`SoftDeleteMacros` must never create foreign keys.

In particular:

```text
deleted_at
```

is not a foreign key.

The `deleted_by` relationship belongs to:

```text
AuditMacros
ForeignKeyMacros
```

---

# 14. Model Integration

The macro operates exclusively at the database-schema level.

It must not:

* import `Illuminate\Database\Eloquent\SoftDeletes`;
* modify models;
* automatically add traits to models;
* change model behavior.

A model requiring soft-delete functionality must explicitly use Laravel's `SoftDeletes` trait.

Example:

```php
use Illuminate\Database\Eloquent\SoftDeletes;

class Product extends BaseModel
{
    use SoftDeletes;
}
```

---

# 15. Naming Rules

The standard column name is:

```text
deleted_at
```

This name must not be changed by individual domains.

If future customization is required, it must be introduced through centralized configuration.

---

# 16. Design Rules

`SoftDeleteMacros` must:

* use strict types;
* remain framework-wide;
* be deterministic;
* create only schema definitions;
* respect the Single Responsibility Principle;
* remain independent of domain models.

---

# 17. Forbidden Behavior

The following behavior is forbidden:

```text
Automatically creating deleted_by
```

```text
Automatically creating indexes
```

```text
Automatically creating foreign keys
```

```text
Automatically enabling Eloquent SoftDeletes
```

```text
Automatically modifying models
```

---

# 18. Testing Requirements

Unit tests must verify:

### Registration

* macro registration succeeds;
* `softDelete()` exists on Blueprint.

### Column

* column name is `deleted_at`;
* column is nullable;
* column type is timestamp.

### Precision

* default precision is respected;
* custom precision is respected where supported.

### Separation

The macro must not create:

* `deleted_by`;
* foreign keys;
* indexes;
* unrelated columns.

### Alias

If `softDeletes()` is implemented, it must produce the same schema definition as `softDelete()`.

# 20. Best Practices

1. Use `softDelete()` for tables that require logical deletion.
2. Do not confuse `deleted_at` with `deleted_by`.
3. Enable Eloquent `SoftDeletes` explicitly at the model level.
4. Do not automatically index every `deleted_at` column.
5. Keep soft-delete schema logic independent from domain logic.

---

# 21. Compatibility

The macro must remain compatible with Laravel's native soft-delete database convention:

```text
deleted_at
```

The implementation must not change Laravel's expected column semantics.
