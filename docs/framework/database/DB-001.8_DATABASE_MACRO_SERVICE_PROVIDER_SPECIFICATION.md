# 1. Purpose

This document defines the official specification for the `DatabaseMacroServiceProvider` component of the MAHLINE Framework.

`DatabaseMacroServiceProvider` is responsible for bootstrapping the MAHLINE Database Blueprint macro system during application startup.

It provides the official integration point between Laravel's service container and `BlueprintMacros`.

---

# 3. Responsibilities

`DatabaseMacroServiceProvider` is responsible for:

* registering the database macro system during application boot;
* calling `BlueprintMacros::register()`;
* providing the Laravel integration point;
* ensuring database macros are available before migrations execute.

It must not:

* implement individual macros;
* contain database schema definitions;
* execute migrations;
* contain business logic;
* depend on Domain models;
* modify migration files.

---

# 4. Dependencies

Required:

```php
Illuminate\Support\ServiceProvider
App\Core\Database\Macros\BlueprintMacros
```

No Domain dependency is permitted.

---

# 5. Provider Lifecycle

The provider uses Laravel's service provider lifecycle.

The official implementation must use:

```php
public function boot(): void
```

for Blueprint macro registration.

---

# 6. Registration Flow

The official registration flow is:

```text
Laravel Application
        │
        ▼
DatabaseMacroServiceProvider
        │
        ▼
boot()
        │
        ▼
BlueprintMacros::register()
        │
        ├── ColumnMacros
        ├── AuditMacros
        ├── ForeignKeyMacros
        ├── IndexMacros
        └── SoftDeleteMacros
```

---

# 7. Official Implementation

The provider should remain intentionally small.

Conceptually:

```php
<?php

declare(strict_types=1);

namespace App\Core\Providers;

use App\Core\Database\Macros\BlueprintMacros;
use Illuminate\Support\ServiceProvider;

final class DatabaseMacroServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        BlueprintMacros::register();
    }
}
```

No individual macro registration should occur directly inside this provider.

---

# 8. `register()` Method

The provider does not need to register services in the container for V1.

Therefore:

```php
public function register(): void
{
    //
}
```

is acceptable.

The important operation occurs during:

```php
boot()
```

---

# 9. Provider Registration

The provider must be registered through Laravel's official application provider mechanism.

The exact registration mechanism must follow the Laravel version used by MAHLINE.

The provider must not be manually instantiated throughout the application.

---

# 10. Execution Timing

The provider must register macros before any migration or schema-building operation that relies on them.

Expected lifecycle:

```text
Application Bootstrap
        ↓
Service Providers Boot
        ↓
DatabaseMacroServiceProvider
        ↓
BlueprintMacros
        ↓
Blueprint macros available
        ↓
Migrations / Schema operations
```

---

# 11. Idempotency

The provider must be safe within Laravel's normal provider lifecycle.

`BlueprintMacros` remains responsible for protecting against duplicate registration.

The provider must not maintain its own duplicate-registration mechanism.

---

# 12. Error Handling

If `BlueprintMacros::register()` throws an exception, the provider must not silently suppress it.

The application must fail during bootstrap with the original error available for diagnosis.

Forbidden:

```php
try {
    BlueprintMacros::register();
} catch (\Throwable) {
    //
}
```

Silent failures are prohibited.

---

# 13. Configuration

Database macro configuration is stored in:

```text
config/database_macros.php
```

The provider must not duplicate configuration values.

For example, it must not contain:

```php
$defaultDeleteAction = 'restrict';
```

Configuration belongs to:

```text
config/database_macros.php
```

and is consumed by the relevant macro implementation.

---

# 14. Separation of Responsibilities

The architecture must remain:

```text
DatabaseMacroServiceProvider
        ↓
Bootstrap / lifecycle

BlueprintMacros
        ↓
Macro family orchestration

ColumnMacros
AuditMacros
ForeignKeyMacros
IndexMacros
SoftDeleteMacros
        ↓
Individual macro implementation
```

Each layer has one responsibility.

---

# 15. Forbidden Dependencies

The provider must never depend on:

```text
Domains/
Models/
Repositories/
Services/
Controllers/
Requests/
Policies/
```

The provider belongs to the Core infrastructure layer.

---

# 16. Testing Requirements

Tests must verify:

### Provider Instantiation

The provider can be instantiated by Laravel.

### Boot

Calling:

```php
$provider->boot();
```

successfully registers the database macros.

### Macro Availability

After boot, expected Blueprint macros must exist.

### Failure Propagation

Registration errors must not be silently swallowed.

---

# 17. Integration Test

A framework-level integration test should verify:

```php
app()->booted();
```

followed by a schema operation using a MAHLINE macro.

Example:

```php
Schema::create('test_table', function (Blueprint $table) {
    $table->ulidPrimary();

    $table->status();

    $table->softDelete();
});
```

The operation must succeed without manually calling:

```php
BlueprintMacros::register();
```

---

# 18. Performance

The provider must perform only the required registration operation during application boot.

It must not:

* query the database;
* inspect database tables;
* load Domain models;
* execute migrations;
* perform filesystem scans.

---

# 19. Future Extensions

Future database infrastructure providers may include:

```text
DatabaseConnectionServiceProvider
DatabaseMacroServiceProvider
DatabaseGrammarServiceProvider
DatabaseHealthServiceProvider
```

These must remain separate responsibilities.

---

# 20. Best Practices

1. Keep the provider minimal.
2. Register macros during `boot()`.
3. Delegate all macro registration to `BlueprintMacros`.
4. Never implement macros inside the provider.
5. Never swallow registration errors.
6. Keep the provider independent from Domains.
7. Use `config/database_macros.php` for configurable behavior.
