# 1. Purpose

This document defines the official specification for the `ForeignKeyMacros` component of the MAHLINE Framework.

`ForeignKeyMacros` extends Laravel's `Blueprint` by registering reusable macros that standardize foreign key creation across all database migrations.

Its objectives are to:

* eliminate duplicated foreign key definitions;
* enforce MAHLINE database conventions;
* provide a strongly typed API using `ForeignKeyAction`;
* simplify migration code;
* ensure consistency across all domains.

# 3. Responsibilities

`ForeignKeyMacros` is responsible for:

* registering foreign key macros;
* creating foreign key constraints;
* applying default MAHLINE conventions;
* supporting configurable update/delete actions.

It must not:

* create audit columns;
* create timestamps;
* create indexes unrelated to foreign keys;
* contain business logic.

# 6. Official Macros

## foreignUlid()

```php
$table->foreignUlid(
    column: 'user_id',
    table: 'users'
);
```

Creates:

* ULID column
* foreign key
* references('id')
* on('users')

Default actions come from the framework configuration.

---

## foreignUuid()

```php
$table->foreignUuid(
    column: 'external_id',
    table: 'external_systems'
);
```

---

## auditForeignKeys()

Creates foreign keys for:

* created_by
* updated_by
* deleted_by

using the configured audit user table.

---

# 7. Default Conventions

Unless explicitly overridden:

Reference column:

```text
id
```

Update action:

```text
Cascade
```

Delete action:

```text
Restrict
```

Configuration may override these defaults.

---

# 8. ForeignKeyAction Integration

The API accepts:

```php
ForeignKeyAction::Cascade
ForeignKeyAction::Restrict
ForeignKeyAction::SetNull
ForeignKeyAction::NoAction
```

Raw string values should be avoided.

---

# 9. Naming Rules

Foreign key columns should follow:

```text
user_id
product_id
invoice_id
country_id
```

Audit columns:

```text
created_by
updated_by
deleted_by
```

---

# 10. Return Type

Macros must return the underlying Blueprint definition where applicable to support fluent chaining.

---

# 11. Design Rules

Macros must:

* use strict types;
* be deterministic;
* avoid hidden behavior;
* respect SRP;
* remain framework-wide reusable.

---

# 12. Performance

Macros must register only once during application boot.

# 16. Usage Examples

Default:

```php
$table->foreignUlid(
    column: 'user_id',
    table: 'users'
);
```

Custom actions:

```php
$table->foreignUlid(
    column: 'category_id',
    table: 'categories',
    onDelete: ForeignKeyAction::SetNull,
    onUpdate: ForeignKeyAction::Cascade,
);
```

---

# 17. Best Practices

* Always use framework macros instead of manual foreign key definitions.
* Prefer `ForeignKeyAction` over raw strings.
* Keep foreign key definitions explicit and consistent.
* Follow MAHLINE naming conventions.
