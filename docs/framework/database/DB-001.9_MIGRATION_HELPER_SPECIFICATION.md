# 1. Purpose

This document defines the official specification for the `MigrationHelper` component of the MAHLINE Framework.

`MigrationHelper` provides reusable, framework-level utilities for migration-related operations.

Its purpose is to centralize common migration concerns without placing database business logic inside individual migration files.

# 3. Responsibilities

`MigrationHelper` is responsible for providing reusable utilities related to migration development.

It may handle:

* standardized migration checks;
* table existence checks;
* column existence checks;
* safe schema operations;
* migration naming utilities;
* common migration validation;
* framework-level migration helpers.

It must not:

* contain domain business logic;
* execute application services;
* access HTTP requests;
* depend on Controllers;
* depend on Domain Models;
* replace Laravel's migration system.

---

The V1 API is intentionally minimal.

Checks whether a table exists.


Return type:

# 8. Safe Operations

The helper may provide safe wrappers for schema operations when required.

Example:

```php
MigrationHelper::dropTableIfExists('temporary_table');
```

Example:

```php
MigrationHelper::dropColumnIfExists(
    table: 'users',
    column: 'legacy_field',
);
```

These operations must remain explicit.

---

# 9. Migration Philosophy

MAHLINE migrations must remain:

* deterministic;
* reversible where possible;
* readable;
* explicit;
* independent from application runtime state.

MigrationHelper must never hide significant schema changes.

Forbidden:

```php
MigrationHelper::autoDetectAndModifySchema();
```

---

# 10. Migration Safety

The helper may assist with defensive operations such as:

```php
Schema::hasTable()
```

and:

```php
Schema::hasColumn()
```

However, normal MAHLINE migrations should not excessively depend on existence checks.

Example preferred migration:

```php
Schema::create('users', function (Blueprint $table) {
    $table->ulidPrimary();
});
```

rather than:

```php
if (!MigrationHelper::hasTable('users')) {
    Schema::create(...);
}
```

MigrationHelper provides tools; it does not replace proper migration sequencing.

---

# 11. Transaction Awareness

`MigrationHelper` must not automatically start or commit database transactions.

Transaction handling belongs to Laravel's migration infrastructure and database driver.

The helper must not introduce hidden transaction behavior.

---

# 12. Connection Handling

If a migration explicitly uses another database connection, the helper must support an optional connection parameter.

Example:

```php
MigrationHelper::hasTable(
    table: 'users',
    connection: 'tenant',
);
```

Default:

```text
null
```

means the application's default database connection.

---

# 13. Error Handling

The helper must not silently suppress database exceptions.

Invalid database operations must propagate their original exceptions.

Forbidden:

```php
try {
    // schema operation
} catch (\Throwable) {
    return false;
}
```

unless the method's explicit purpose is a non-throwing existence check.

# 19. Performance

The helper must not:

* scan all tables unnecessarily;
* execute repeated schema queries without reason;
* cache schema information indefinitely;
* perform database operations during application boot.

It is a migration utility and should normally execute only when explicitly called.

---

# 20. Forbidden Features in V1

```text

Automatic schema synchronization
Automatic schema repair
Automatic migration execution
Automatic rollback
Schema diff engine
Database deployment engine
```

These features would require separate architecture and specifications.

# 22. Usage Example

A migration may use:

```php
return new class extends Migration
{
    public function up(): void
    {
        if (!MigrationHelper::hasTable('countries')) {
            Schema::create('countries', function (Blueprint $table) {
                $table->ulidPrimary();
                $table->code();
                $table->status();
                $table->auditColumns();
                $table->softDelete();
            });
        }
    }

    public function down(): void
    {
        Schema::dropIfExists('countries');
    }
};
```

However, existence checks should only be used when genuinely required.

---

# 23. Best Practices

1. Prefer Laravel's native migration API.
2. Use `MigrationHelper` only for repeated migration concerns.
3. Keep migrations readable.
4. Never hide important schema changes.
5. Never place domain logic in the helper.
6. Do not use the helper as a schema synchronization engine.
7. Keep migration operations deterministic.
