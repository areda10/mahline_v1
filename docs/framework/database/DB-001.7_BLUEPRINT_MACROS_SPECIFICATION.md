## MAHLINE Framework V1

**Version:** 1.0
**Status:** Frozen
**Component:** Core Database
**Identifier:** DB-001.7

---

# 1. Purpose

This document defines the official specification for the `BlueprintMacros` component of the MAHLINE Framework.

`BlueprintMacros` is the central registry responsible for registering all MAHLINE database Blueprint macro families.

It acts as an orchestration layer.

It does not contain the implementation of individual macros.

---

# 2. Location

Source code:

```text
app/
└── Core/
    └── Database/
        └── Macros/
            └── BlueprintMacros.php
```

Namespace:

```php
App\Core\Database\Macros
```

---

# 3. Responsibilities

`BlueprintMacros` is responsible for:

* registering all approved MAHLINE Blueprint macro families;
* ensuring registration happens through a single entry point;
* maintaining the registration order;
* preventing duplicate registration when required.

It must not:

* implement individual macros;
* contain database business logic;
* create migrations;
* create tables;
* execute SQL queries;
* depend on Domain classes.

---

# 4. Macro Families

The following macro families are officially registered by V1:

```text
ColumnMacros
AuditMacros
ForeignKeyMacros
IndexMacros
SoftDeleteMacros
```

Registration flow:

```text
BlueprintMacros
      │
      ├── ColumnMacros
      ├── AuditMacros
      ├── ForeignKeyMacros
      ├── IndexMacros
      └── SoftDeleteMacros
```

---

# 5. Dependencies

Required:

```php
App\Core\Database\Macros\ColumnMacros
App\Core\Database\Macros\AuditMacros
App\Core\Database\Macros\ForeignKeyMacros
App\Core\Database\Macros\IndexMacros
App\Core\Database\Macros\SoftDeleteMacros
```

No Domain dependency is permitted.

---

# 6. Public API

The component exposes one official entry point:

```php
public static function register(): void;
```

Usage:

```php
BlueprintMacros::register();
```

---

# 7. Registration Order

The official V1 registration order is:

```text
1. ColumnMacros
2. AuditMacros
3. ForeignKeyMacros
4. IndexMacros
5. SoftDeleteMacros
```

This order reflects conceptual dependencies.

---

# 8. Idempotency

Calling:

```php
BlueprintMacros::register();
```

more than once must not result in an invalid application state.

The implementation must protect against duplicate macro registration where necessary.

---

# 9. Separation of Responsibilities

`BlueprintMacros` is an orchestrator only.

For example, the following implementation style is forbidden:

```php
Blueprint::macro('status', function () {
    // complete implementation here
});
```

inside `BlueprintMacros`.

Instead:

```php
ColumnMacros::register();
```

must contain the implementation.

---

# 10. Registration Architecture

Conceptually:

```php
public static function register(): void
{
    ColumnMacros::register();

    AuditMacros::register();

    ForeignKeyMacros::register();

    IndexMacros::register();

    SoftDeleteMacros::register();
}
```

The actual implementation may add an internal protection mechanism if Laravel's macro system requires it.

---

# 11. Laravel Integration

`BlueprintMacros` operates on Laravel's:

```php
Illuminate\Database\Schema\Blueprint
```

It must not replace Laravel's Blueprint class.

It extends Laravel behavior through the framework's macro mechanism.

---

# 12. Configuration

Macro behavior may depend on:

```text
config/database_macros.php
```

However, configuration resolution should remain inside the individual macro families whenever possible.

`BlueprintMacros` should not contain configuration-specific business logic.

---

# 13. Error Handling

If a required macro family cannot be registered, the application bootstrap process must fail clearly.

Errors must identify:

* the failed macro family;
* the registration stage;
* the underlying exception.

Silent registration failures are forbidden.

---

# 14. Performance

Registration should occur once during application bootstrap.

After registration, normal Blueprint usage must not incur unnecessary registration overhead.

---

# 15. Testing Requirements

Tests must verify:

### Registration

* `register()` executes successfully;
* all macro families are registered.

### Availability

After registration:

```php
Blueprint::hasMacro(...)
```

must confirm the expected macros exist.

### Idempotency

Calling:

```php
BlueprintMacros::register();
BlueprintMacros::register();
```

must not break the application.

### Separation

`BlueprintMacros` must not directly implement individual database macros.

---

# 16. Forbidden Dependencies

`BlueprintMacros` must never depend directly on:

```text
Domains/
Models/
Repositories/
Services/
Controllers/
Requests/
Policies/
```

It belongs entirely to the Core infrastructure layer.

---

# 17. Future Extensions

Future macro families may include:

```text
JsonMacros
EnumMacros
SpatialMacros
PartitionMacros
SearchMacros
```

They must be introduced through dedicated classes.

They must not be implemented directly inside `BlueprintMacros`.

---

# 18. Usage

The preferred application-level usage is through:

```php
DatabaseMacroServiceProvider
```

rather than manually calling `BlueprintMacros::register()` throughout the application.

Example architecture:

```text
Application Bootstrap
        │
        ▼
DatabaseMacroServiceProvider
        │
        ▼
BlueprintMacros::register()
        │
        ├── ColumnMacros
        ├── AuditMacros
        ├── ForeignKeyMacros
        ├── IndexMacros
        └── SoftDeleteMacros
```

---

# 19. Best Practices

1. Keep `BlueprintMacros` extremely small.
2. Never put individual macro implementations inside it.
3. Register each macro family exactly once.
4. Keep registration order deterministic.
5. Keep the registry independent from Domains.
6. Use the service provider as the normal bootstrap entry point.
