# 1. Purpose

This document defines the official specification for the `ForeignKeyAction` enum used by the MAHLINE Framework.

The enum standardizes foreign key actions across the entire framework and replaces hard-coded string values.

---

# 2. Location

```text
app/
└── Core/
    └── Enums/
        └── Database/
            └── ForeignKeyAction.php
```

Namespace:

```php
App\Core\Enums\Database
```

---

# 3. Responsibilities

The enum is responsible for:

* representing supported foreign key actions;
* providing a strongly typed API;
* eliminating hard-coded SQL action strings;
* ensuring consistency across migrations and database helpers;
* integrating with the MAHLINE enum foundation.

---

# 4. Dependencies

The enum depends on:

* `BaseEnum`
* `BaseEnumContract`
* `InteractsWithEnum`

No business domain dependency is allowed.

---

# 5. Enum Type

```php
enum ForeignKeyAction: string
```

---

# 6. Cases

The enum defines the following cases:

| Case     | Database Value |
| -------- | -------------- |
| Cascade  | cascade        |
| Restrict | restrict       |
| NoAction | no action      |
| SetNull  | set null       |

These values match SQL foreign key actions.

---

# 7. Public API

The enum inherits the common API from `BaseEnum`.

Available methods include:

* values()
* names()
* options()
* labels()
* fromValue()
* tryFromValue()
* has()
* is()
* equals()

The enum must implement:

```php
public function label(): string;
```

Human-readable labels:

---

# 9. Usage

Example:

```php
$table
    ->foreignUlid('user_id')
    ->references('id')
    ->on('users')
    ->onDelete(ForeignKeyAction::Cascade->value);
```

Future MAHLINE macros may also accept the enum directly.

---

# 10. Integration

The enum is intended to be used by:

* ColumnMacros
* ForeignKeyMacros
* MigrationHelper
* Database generators
* Future migration builders

It may also be used by development tools and code generators.

---

# 11. Validation Rules

The enum guarantees:

* only valid foreign key actions are used;
* compile-time type safety where possible;
* centralized management of supported actions.

---

# 12. Design Rules

The enum must:

* be immutable;
* use strict types;
* never contain business logic;
* remain framework-agnostic;
* expose only database-related behavior.

---

# 13. Extensibility

Future SQL actions may be added without breaking the public API, provided they are supported by the target database engines.

Existing values must remain backward compatible.

---

---

# 15. Documentation Requirements

Documentation must include:

* purpose;

---

# 16. Best Practices

* Use the enum instead of raw strings.
* Keep database actions centralized.
* Avoid magic values in migrations.
* Prefer enum-based APIs in helper classes and macros.
