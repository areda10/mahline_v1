# 1. Purpose

This document defines the official specification for the `HasAuditColumns` component of the MAHLINE Framework.

`HasAuditColumns` provides a reusable mechanism for identifying models that use the standard MAHLINE audit columns.

The component establishes a consistent contract between:

* Eloquent models;
* audit infrastructure;
* database audit columns;
* future audit services.

---

# 2. Architectural Clarification

`HasAuditColumns` is a **model-level concern**.

It must not create database columns.

Database column creation is handled by:

```text
AuditMacros
```

Therefore:

```text
AuditMacros
    ↓
Database schema

HasAuditColumns
    ↓
Eloquent model behavior
```

These responsibilities must remain separate.

# 4. Responsibilities

`HasAuditColumns` is responsible for defining the standard audit-column contract for Eloquent models.

The concern may provide accessors, relationships, and helper methods related to:

```text
created_by
updated_by
deleted_by
```

It must not:

* create database columns;
* run migrations;
* register Blueprint macros;
* contain authentication logic;
* contain authorization logic;
* contain business logic.

---

# 5. Standard Audit Columns

MAHLINE V1 defines:

```text
created_by
updated_by
deleted_by
```

as the standard actor-reference columns.

All three columns use ULID values.

All three columns are nullable.

---

# 6. Database Responsibility

The columns are created through:

```php
$table->auditColumns();
```

provided by:

```text
AuditMacros
```

The corresponding foreign key constraints are handled by:

```text
ForeignKeyMacros
```

This means:

```text
AuditMacros
    ↓
created_by
updated_by
deleted_by

ForeignKeyMacros
    ↓
Foreign key constraints

HasAuditColumns
    ↓
Eloquent model integration
```

---

# 7. Model Contract

A model using `HasAuditColumns` declares that it participates in the MAHLINE audit system.

Example:

```php
use App\Core\Database\Concerns\HasAuditColumns;

class Product extends BaseModel
{
    use HasAuditColumns;
}
```

---

# 8. Audit Relationships

The concern may provide standardized relationships to the user model.

Conceptually:

```php
public function createdBy(): BelongsTo
{
    return $this->belongsTo(
        User::class,
        'created_by'
    );
}
```

```php
public function updatedBy(): BelongsTo
{
    return $this->belongsTo(
        User::class,
        'updated_by'
    );
}
```

```php
public function deletedBy(): BelongsTo
{
    return $this->belongsTo(
        User::class,
        'deleted_by'
    );
}
```

However, the Core implementation must not introduce a hard dependency on the Identity `User` model.

The user model must therefore be resolved through the official MAHLINE authentication/user contract or configurable model binding.

---

# 9. Core / Identity Boundary

The following dependency is forbidden:

```text
Core
  ↓
Domains\Identity\Models\User
```

The preferred dependency direction is:

```text
Core
  ↓
Contract / configuration

Identity
  ↓
Concrete User implementation
```

This preserves the independence of the Core layer.

---

# 10. Configuration

The audit user model/reference may be configured centrally.

The database configuration already defines:

```php
'audit' => [
    'user_table' => 'users',
    'user_primary_key' => 'id',
],
```

Any Eloquent model resolution must use the appropriate Identity/Auth contract or centralized configuration.

No model name should be hard-coded inside the trait.

---

# 11. Audit Accessors

The component may expose:

```php
$model->createdBy;
$model->updatedBy;
$model->deletedBy;
```

through Eloquent relationships.

It may also provide:

```php
$model->createdById();
$model->updatedById();
$model->deletedById();
```

if required by the final implementation.

These methods must remain read-oriented in V1.

---

# 12. Automatic Audit Population

`HasAuditColumns` does **not** automatically populate audit columns in V1.

The following behavior is outside the responsibility of this concern:

```text
created_by = authenticated user
updated_by = authenticated user
deleted_by = authenticated user
```

Automatic population belongs to the dedicated audit infrastructure.

This avoids coupling database model behavior directly to authentication state.

---

# 13. Request Independence

The concern must never depend directly on:

```php
Illuminate\Http\Request
```

or:

```php
request()
```

Audit information must be supplied by the appropriate application-level audit service.

This follows the MAHLINE rule that Core services and model infrastructure must remain independent from HTTP requests.

---

# 14. Soft Delete Integration

`HasAuditColumns` and soft deletes are separate concerns.

A model may use both:

```php
use HasAuditColumns;
use SoftDeletes;
```

The responsibilities are:

```text
HasAuditColumns
    ↓
created_by
updated_by
deleted_by

SoftDeletes
    ↓
deleted_at
```

`HasAuditColumns` must not automatically enable `SoftDeletes`.

---

# 15. Required Database Schema

A model using `HasAuditColumns` is expected to have:

```text
created_by
updated_by
deleted_by
```

in its database table.

The migration should use:

```php
$table->auditColumns();
```

and the appropriate foreign-key macros.

---

# 16. Nullability

All audit actor references are nullable.

This allows records to exist when:

* no authenticated actor exists;
* data is imported;
* a system process creates the record;
* historical data is migrated;
* an actor has been removed or anonymized according to system rules.

---

# 17. Deletion Rules

`deleted_by` must not be confused with `deleted_at`.

```text
deleted_at
    ↓
When the record was soft deleted

deleted_by
    ↓
Who performed the deletion
```

Both may exist simultaneously.

---

# 18. Testing Requirements

Unit tests must verify:

### Trait Usage

A model can use:

```php
HasAuditColumns
```

without errors.

### Relationships

The standard audit relationships are correctly configured.

### Column Names

The relationships use:

```text
created_by
updated_by
deleted_by
```

### Nullability

The model can operate with nullable audit actor references.

### Independence

The concern must not require an HTTP Request.

### Core Independence

The concern must not directly import a Domain Identity model.

---

# 19. Integration Testing

A framework integration test should use a test model:

```php
class AuditTestModel extends BaseModel
{
    use HasAuditColumns;
}
```

The test should verify that:

```php
$model->createdBy;
$model->updatedBy;
$model->deletedBy;
```

resolve correctly when corresponding relationships are configured.

---

# 20. Forbidden Behavior

The following behavior is forbidden:

```text
Automatically reading request()
```

```text
Automatically querying the authenticated user
```

```text
Automatically writing created_by during model creation
```

```text
Automatically writing updated_by during model updates
```

```text
Automatically writing deleted_by during deletion
```

```text
Creating database columns from the trait
```

```text
Importing Domains\Identity\Models\User directly
```

# 22. Relationship With Audit Infrastructure

The intended future architecture is:

```text
Authentication Context
        │
        ▼
Audit Context
        │
        ▼
Audit Service
        │
        ▼
Eloquent Model
        │
        ▼
HasAuditColumns
        │
        ▼
created_by / updated_by / deleted_by
```

`HasAuditColumns` is therefore an integration point, not the complete audit system.

---

# 23. Best Practices

1. Use `HasAuditColumns` on models participating in the audit system.
2. Create the corresponding columns through `AuditMacros`.
3. Create constraints through `ForeignKeyMacros`.
4. Keep actor population outside the trait.
5. Never depend on HTTP Request state.
6. Keep Core independent from Identity implementations.
7. Keep `deleted_by` separate from `deleted_at`.
