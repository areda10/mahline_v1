# 1. Purpose

This document defines the official specification for the `IndexMacros` component of the MAHLINE Framework.

`IndexMacros` provides reusable Laravel Blueprint macros for creating standardized database indexes.

Its objectives are to:

* centralize index creation;
* enforce MAHLINE naming conventions;
* avoid duplicated index definitions;
* improve migration readability;
* provide consistent indexing across all domains;
* prevent accidental duplicate or ambiguous index names.

---


Namespace:

```php
App\Core\Database\Macros
```

---

# 3. Responsibilities

`IndexMacros` is responsible for:

* registering index-related Blueprint macros;
* creating standard indexes;
* creating unique indexes;
* creating composite indexes;
* creating standard audit indexes;
* generating consistent index names.

It must not:

* create columns;
* create foreign keys;
* create audit columns;
* contain business logic;
* decide which fields require indexing.

The decision to index a business field belongs to the database design of the corresponding domain.

---

# 4. Dependencies

Required:

```text
Illuminate\Database\Schema\Blueprint
```

Optional:

```text
config/database_macros.php
```

No domain dependency is allowed.

---

# 5. Registration

The component exposes one public registration method:

```php
public static function register(): void;
```

All index macros must be registered through this method.

# 6. Official V1 Macros

## 6.1 indexColumns()

Creates a standard index.

```php
$table->indexColumns(['status']);
```

Equivalent intent:

```php
$table->index(['status']);
```

---

## 6.2 uniqueColumns()

Creates a unique index.

```php
$table->uniqueColumns(['email']);
```

Equivalent intent:

```php
$table->unique(['email']);
```

---

## 6.3 compositeIndex()

Creates an index over multiple columns.

```php
$table->compositeIndex([
    'country_id',
    'status',
]);
```

Equivalent intent:

```php
$table->index([
    'country_id',
    'status',
]);
```

---

## 6.4 compositeUnique()

Creates a unique composite index.

```php
$table->compositeUnique([
    'cooperative_id',
    'code',
]);
```

Equivalent intent:

```php
$table->unique([
    'cooperative_id',
    'code',
]);
```

---

## 6.5 auditIndexes()

Creates indexes for standard audit columns.

```php
$table->auditIndexes();
```

Default indexed columns:

```text
created_by
updated_by
deleted_by
```

This macro does not create the columns themselves.

---

# 7. Index Naming

MAHLINE uses Laravel's default index naming strategy unless an explicit name is provided.

Example:

```php
$table->index(
    ['country_id', 'status'],
    'countries_status_index'
);
```

When custom naming is supported by a macro, the name must be:

* deterministic;
* descriptive;
* unique within the table;
* written in snake_case.

---

# 8. Explicit Naming

Macros should support an optional index name where Laravel permits it.

Example:

```php
$table->indexColumns(
    ['status'],
    'products_status_index'
);
```

No automatic custom naming algorithm should override an explicitly supplied name.

---

# 9. Composite Index Rules

Column order is significant.

For example:

```php
$table->compositeIndex([
    'cooperative_id',
    'status',
]);
```

is different from:

```php
$table->compositeIndex([
    'status',
    'cooperative_id',
]);
```

The order must therefore be preserved exactly as supplied.

---

# 10. Unique Index Rules

A unique index must only be used when the database design explicitly requires uniqueness.

Example:

```php
$table->uniqueColumns(['email']);
```

should not be used merely for query optimization.

---

# 11. Audit Index Rules

`auditIndexes()` operates only on existing audit columns.

It must not create:

```text
created_by
updated_by
deleted_by
```

Column creation belongs to `AuditMacros`.

This separation preserves the Single Responsibility Principle.

---

# 12. Nullability

Index macros must not modify the nullability of the indexed columns.

They operate only on indexes.

---

# 13. Foreign Keys

Index macros must not create foreign keys.

Foreign key creation belongs exclusively to:

```text
ForeignKeyMacros
```

---

# 14. Performance Rules

Index creation must consider:

* query patterns;
* cardinality;
* table size;
* composite column order;
* write overhead.

The framework provides the mechanism for creating indexes, but does not automatically index every column.

---

# 15. Design Rules

`IndexMacros` must:

* use strict types;
* remain framework-wide;
* be deterministic;
* avoid hidden indexes;
* avoid business logic;
* preserve Laravel compatibility;
* support fluent migration syntax.

---

# 16. Forbidden Behavior

The following behavior is forbidden:

```text
Automatically indexing every column
```

```text
Automatically creating indexes for every foreign key
```

```text
Automatically creating unique indexes
```

```text
Modifying existing columns
```

```text
Adding business-specific indexing rules
```

---

# 17. Testing Requirements

Unit tests must verify:

### Registration

* macro registration succeeds;
* macros are available on Blueprint.

### Standard Index

* correct column is indexed;
* custom name is respected.

### Unique Index

* unique constraint is generated;
* custom name is respected.

### Composite Index

* multiple columns are preserved in order.

### Composite Unique

* multiple columns are preserved in order;
* uniqueness is enforced.

### Audit Indexes

* `created_by` is indexed;
* `updated_by` is indexed;
* `deleted_by` is indexed.

### Separation

Tests must ensure index macros do not create:

* columns;
* foreign keys;
* unrelated constraints.

# 18. Usage Examples

## Standard index

```php
Schema::create('products', function (Blueprint $table) {
    $table->ulidPrimary();

    $table->status();

    $table->indexColumns([
        'status',
    ]);
});
```

---

```php
$table->uniqueColumns([
    'email',
]);
```

---

## Composite index

```php
$table->compositeIndex([
    'cooperative_id',
    'status',
]);
```

---

## Composite unique

```php
$table->compositeUnique([
    'cooperative_id',
    'code',
]);
```

---

## Audit indexes

```php
$table->auditColumns();

```

# 19. Best Practices

1. Index according to real query requirements.
2. Prefer meaningful composite indexes.
3. Keep composite column order intentional.
4. Use unique indexes only when uniqueness is required.
5. Avoid unnecessary indexes on frequently written tables.
6. Keep index creation separate from column creation.
7. Use explicit names when a migration requires stable index naming.

---

# 20. Compatibility

`IndexMacros` must remain compatible with Laravel's native Blueprint index behavior.

The macros are an abstraction layer and must not change the underlying database semantics.
